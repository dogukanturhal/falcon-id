# Migration authoring (Falcon-ID)

Falcon-ID's migrations live under `migrations/` as paired
`NNN_name.up.sql` / `NNN_name.down.sql` files. **Public-schema
lifecycle is now owned by Keystone** — the canonical authoring path
is to edit the SchemaDefinition CR at
`<gitops-repo>/keystone/resources/falcon-id/schema-definition-main.yaml`
and let Keystone's differ emit the bundle, run it through the
SchemaPolicy/ApprovalPolicy gate, and apply.

The remaining users of these SQL files are the per-tenant provisioner
paths (`internal/services/realm_db_*` + `provisioning_orchestrator`)
which still apply the embedded FS when seeding a new tenant database.
That coupling will be cut once tenant provisioning routes through
Keystone too.

The 5 standards below MUST be followed by every PR that adds or
modifies a migration. They're enforced by `make sql-lint` (CI gate;
landed in falcon-id !97 after the 2026-05-01 oauth_client_columns
whitespace incident) and by Keystone's cluster-side analyzer when the
bundle reaches `MigrationPlan.status.findings`.

The canonical reference for the WHY behind each rule lives in
[keystone/docs/migration-authoring.md](https://github.com/dogukanturhal/keystone/-/blob/main/docs/migration-authoring.md).
This file is the **falcon-id-flavoured short version** with project-
specific paths and tooling.

## The 5 standards

### 1. `keystone.sum` integrity manifest

Generate after every migration change:

```bash
cd migrations/
keystonectl sum .          # writes/updates keystone.sum
git add keystone.sum
```

The cluster reconciler refuses to apply a bundle whose `keystone.sum`
doesn't match the live `*.sql` files. CI also re-generates and diffs
the file as a `make sql-lint` step.

### 2. `SET LOCAL statement_timeout = '30s'` per file

Top of every `*.up.sql` AND `*.down.sql`:

```sql
SET LOCAL statement_timeout = '30s';
```

Override per-file for legitimately heavy operations (`'15min'` for a
non-`CONCURRENTLY` index build on a small table, etc.) — the timeout
shows up in code review.

### 3. `GENERATED BY DEFAULT AS IDENTITY` not `SERIAL`

```sql
-- DO
CREATE TABLE oauth_clients (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ...
);

-- DON'T
CREATE TABLE oauth_clients (
    id BIGSERIAL PRIMARY KEY,
    ...
);
```

`BIGINT GENERATED BY DEFAULT AS IDENTITY` is SQL-standard, has clean
sequence ownership, and avoids the int4 overflow class (~2.1B rows).

### 4. No `public.` prefix on table names

```sql
-- DO
CREATE TABLE oauth_clients (...);
CREATE INDEX idx_oc_first_party ON oauth_clients(is_first_party);

-- DON'T
CREATE TABLE public.oauth_clients (...);
```

The Keystone runner sets `search_path = <target_schema>, pg_catalog`
before applying. Hardcoding `public.` defeats multi-tenant
portability — the same migration file MUST land cleanly into a
tenant-specific schema if/when Falcon-ID grows multi-tenant.

Cross-schema references are the only legitimate qualifier (`audit.
events` from a trigger in `oauth.*`); document the cross-reference
in a comment.

### 5. Pair `*.up.sql` with `*.down.sql`, both `IF EXISTS`-safe

Every up file MUST have a corresponding down file. Down statements
MUST use `IF EXISTS`:

```sql
-- 042_create_oauth_clients.down.sql
SET LOCAL statement_timeout = '30s';

DROP INDEX IF EXISTS idx_oc_first_party;
DROP TABLE IF EXISTS oauth_clients;
```

For genuinely irreversible changes (e.g., dropping a 1B-row table),
the down file SHOULD still exist with an explicit no-op + a pointer
to the archive procedure:

```sql
-- 099_drop_legacy_sessions.down.sql
SELECT 'irreversible: see migrations/099_drop_legacy_sessions.md for archive procedure' AS rollback_note;
```

## Local development

```bash
# 1. Pick the next migration number
NEXT=$(printf '%03d' $(( $(ls migrations/*.up.sql 2>/dev/null | wc -l) + 1 )))

# 2. Create up + down stubs
touch migrations/${NEXT}_my_change.up.sql
touch migrations/${NEXT}_my_change.down.sql

# 3. Author the SQL (5 standards above)

# 4. Lint locally before commit
make sql-lint

# 5. Update keystone.sum
keystonectl sum migrations/

# 6. Commit
git add migrations/ && git commit -m "feat: add my_change migration"
```

## CI integration

`hack/sql-lint` (called by `make sql-lint`) runs:

  1. **boundary-whitespace** check — catches the
     2026-05-01-class concat bug where `*Columns` raw-string
     constants run together via `+` between `SELECT` and `FROM`.
     Pre-merge gate; `allow_failure: false`.
  2. **schema-drift** check — diffs migrations against runtime
     repo SELECTs to catch table/column rename mismatches (the
     2026-04-24 iam_oauth_tokens.token_type incident).
  3. **5-standards** check — keystone.sum freshness +
     statement_timeout + GENERATED BY DEFAULT + no `public.` +
     up/down pairing + IF EXISTS.

Cluster-side after merge:

  - The release CI's `migration-bundle` stage (FF12, !118 in this
    project) runs `hack/render-migration-bundle.sh --tag <git-tag>
    --since <last-bundled-version>` and emits the MigrationBundle
    YAML to the GitOps repository.
  - Keystone's cluster-side analyzer surfaces findings on
    `MigrationPlan.status.findings`. SchemaPolicy in `Audit` mode
    keeps applying with warnings; `Enforce` rejects bundles with
    non-empty findings.
